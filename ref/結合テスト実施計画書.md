## 1. 目的

本計画書は、Here's Me Server アプリケーション（JavaScript/Node.js + 一部Java）の結合テストを効率的かつ確実に実施するための実施計画を定義する。

### 1.1 テスト対象システム
- **アーキテクチャ**: 三層レイヤー構成のWebアプリケーション
- **技術スタック**: 
  - フロントエンド層: Vue.js
  - アプリケーション層: Node.js + Express
  - データベース層: PostgreSQL
  - 暗号化処理: Java (EncDec)
- **単体テストカバレッジ**: C0 94.86%, C1 87.41%

### 1.2 結合テストの範囲
単体テストで検証困難な以下の項目を対象とする：
- 外部コンポーネント連携（Java EncDec、AWS SSM）
- データベース実トランザクション
- 旧クライアント（ver2.0以前）の互換性動作
- 複数モジュール間の相互作用

## 2. テスト実施方針

### 2.1 基本方針
1. **バグ未修正での実施**: 単体テストで発見されたバグは修正せずにテストを進める
2. **段階的実施**: 修正不要な項目を優先し、バグ修正後に再テストを実施
3. **実環境志向**: 可能な限り本番に近い環境で実施
4. **自動化の準備**: 将来的な回帰テスト自動化を見据えた設計

### 2.2 テスト実施環境

| 項目 | 開発環境 | 検証環境(AWS) | 備考 |
|------|---------|--------------|------|
| OS | Ubuntu 20.04 LTS | Amazon Linux 2 | - |
| Node.js | v22.14.0 | v22.14.0 | - |
| PostgreSQL | 14.12 | RDS PostgreSQL 14.x | 検証環境のみ |
| Java | OpenJDK 11 | OpenJDK 11 | EncDec実行用 |
| AWS SSM | N/A | 有効 | 検証環境のみ |

### 2.3 テストデータ管理
- **準備**: SQLスクリプトによる初期データ投入
- **実行**: テストケースごとに独立したデータセット
- **クリーンアップ**: テスト後の自動削除（トランザクションロールバック推奨）

## 5. テスト環境構築手順

### 5.1 開発環境セットアップ

#### 5.1.1 PostgreSQL設定
```bash
# テストデータベース作成
createdb heresme_test

# スキーマ適用
psql heresme_test < db/schema.sql

# テストデータ投入
psql heresme_test < db/test_data_integration.sql
```

#### 5.1.2 Java EncDec配置
```bash
# Javaソースのビルド
cd src
mvn clean compile

# クラスファイルのコピー
cp target/classes/com/micros/util/EncDec.class ../util/

# 実行テスト
java -cp util EncDec enc "testpassword"
```

#### 5.1.3 Node.js環境設定
```bash
# 依存パッケージインストール
npm install

# 環境変数設定
export DATABASE_URL="postgresql://user:pass@localhost/heresme_test"
export NODE_ENV="integration-test"
export JAVA_HOME="/usr/lib/jvm/java-11-openjdk"

# アプリケーション起動確認
npm start
```

### 5.2 検証環境(AWS)セットアップ

#### 5.2.1 AWS SSMパラメータストア設定
```bash
# DB接続情報の登録
aws ssm put-parameter \
  --name "heresme.db_auth_info" \
  --value "db.heresme-test.rds.amazonaws.com,5432,heresme_db,dbuser,dbpassword" \
  --type "SecureString" \
  --overwrite \
  --region ap-northeast-1

# 登録確認
aws ssm get-parameter \
  --name "heresme.db_auth_info" \
  --with-decryption \
  --region ap-northeast-1
```

#### 5.2.2 環境変数設定
```bash
# /etc/environment または .env ファイルに設定
ENVIRONMENT_TYPE=1
AWS_REGION=ap-northeast-1
NODE_ENV=integration-test
```

#### 5.2.3 デプロイ確認
```bash
# アプリケーションデプロイ
npm run deploy:integration

# ヘルスチェック
curl http://integration-server.example.com/health
```

## 7. 障害管理

### 7.1 バグ報告フロー

```
発見 → 一次判定 → バグ報告 → 開発確認 → 修正 → 再テスト
  ↓       ↓         ↓         ↓        ↓       ↓
 担当者   TL      GitHub    開発TL    開発者  担当者
           ↓                            ↓
         既知か?                      修正完了
          Yes → ステータス更新のみ
```

### 7.2 バグ重要度分類

| 重要度 | 定義 | 対応期限 |
|-------|------|---------|
| **Critical** | システムが起動しない、データ損失の可能性 | 即日 |
| **High** | 主要機能が動作しない | 3営業日以内 |
| **Medium** | 一部機能に不具合があるが回避可能 | 1週間以内 |
| **Low** | 軽微な不具合、UI/UXの改善提案 | 次バージョンで対応 |

### 7.3 既知のバグの取扱い

単体テストで発見済みのバグ（BUG-001～005）は以下のように扱う：

1. **Phase 1では該当テストケースをスキップ**
   - IT-003, IT-007, IT-008 は実施しない
   - 実施記録に「バグ修正待ち」と明記

2. **バグ修正後にPhase 2で実施**
   - 開発チームから修正完了通知を受領
   - コードレビュー実施
   - テストケース実施

3. **新規バグ発見時**
   - GitHub Issuesに即座に登録
   - 優先度判定会議（毎日15:00）で対応判断

## 9. リスクと対策

### 9.1 想定リスク

| リスク | 発生確率 | 影響度 | 対策 |
|-------|---------|--------|------|
| AWS環境へのアクセス遅延 | 中 | 高 | VPN接続の事前確認、予備日の確保 |
| テストデータ不整合 | 高 | 中 | 自動投入スクリプトの準備、バックアップ取得 |
| Java実行環境の差異 | 低 | 高 | Dockerコンテナ化の検討 |
| 旧クライアントシミュレータ不足 | 中 | 中 | モックツールの準備 |
| 新規バグの大量発見 | 中 | 高 | Phase 1の早期開始、予備日の設定 |

### 9.2 コンティンジェンシープラン

#### ケース1: Critical/Highバグが複数発見された場合
- 即座にステークホルダー会議を招集
- スケジュール再検討（Phase 2の延期も視野）
- 開発リソースの追加投入を検討

#### ケース2: AWS環境が利用不可の場合
- IT-004, IT-005, IT-006 を最優先で実施できるタイミングに移動
- 開発環境でのモック実装による代替テストを検討
- AWSサポートへのエスカレーション

#### ケース3: テストデータ破損
- 毎日のバックアップからリストア
- テストデータ投入スクリプトを再実行
- 影響範囲の特定と再テスト実施
